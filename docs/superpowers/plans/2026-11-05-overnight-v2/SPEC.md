# Make Mosaic Overnight review reliable

Approved November 5, 2026. Repair implementation mode: Codex-only (owner's explicit choice). This is the approved execution specification, not a new brainstorming round. The independent background choice describes the repaired product, not provider spending for this repair.

## Outcome and boundaries

Ordinary prompt → mode choice → approve exact scope and limits → independent background job managing DeepSeek, protected checks, Codex reviews, integration and truthful morning report. Codex is reviewer only within Overnight review, with no silent code rescue. Runtime and skill fixes are required. Preserve Collaborative, Codex-only, DeepSeek-only and historical Overnight review v1 behavior. Research remains parked. Finishing, publishing or retrying the failed internship tracker is separate. No Spark configuration changes, public publishing, new accounts, outreach or budget renewals. Never infer a native persistent Codex Goal from a backend goal.

The owner approved code, tests, documentation, packaging and rollout subject to gates. Installing a tested immutable package is authorized only after actual existing owners and operations are verified quiescent; do not interrupt unrelated jobs. Never edit the installed immutable runtime. Preserve prior packages and records. Roll back software only with v2 quiescent; never restore the database, refund spending or run unfinished v2 work under an old engine.

## 1. Version and isolate

Keep the four names. Introduce overnight_review version 2 as the default for new overnight preparations. Preserve v1 definitions, manifests, hashes, requests, attempts, deadlines and evidence; no automatic migration. Branch changed shared behavior on the pinned overnight version. Hash-bound overnight policy records preflight check IDs, final-only IDs and bounded batching/correction settings. Work only in an isolated candidate from the verified clean coding-core base. Proposed skill defaults: eight-hour goal, at most ten sequential stages, two hours/stage, five attempts, fifty coding requests and two Codex reviews/stage; planner separate, at most three requests. Disclose defaults; narrower owner limits win.

## 2. Preparation, planning and implementation

### Exact preflight

Add overnight_preflight bound to prepared goal ID and exact approval hash. Use a disposable workspace with the real base, tracked inventory, read/write policy, dependencies and actual sandbox. Explicit infrastructure checks verify starter types/build under actual policy, not unfinished feature acceptance. Receipt pins manifest, revision, check definitions, relevant runtime identity and results. Refuse v2 activation without a matching successful receipt; changed inputs invalidate it. Build staging copies approved input inventory, never the root indiscriminately. Fail actionably before any DeepSeek spending.

### Explicit stage gates

Update planning format and validator. Every stage explicitly supplies checks, scoped permissions, dependencies, acceptance and role implementation/final. Missing checks reject rather than inherit all. Exactly one final stage, last, transitively dependent on every earlier stage. Early stages cannot request final-only checks. Final stage runs every project check. Validate the entire graph atomically before creating children. Invalid plans use bounded planner corrections. DeepSeek writes routine assignments and implementation plan; Codex owns product scope, trusted setup and review.

### Multiple batches per attempt

V2 has apply_changes and finish_stage; other modes/v1 retain submit_changes. apply_changes atomically validates/applies a batch and refreshes context without finishing the stage or spending another attempt. Two files/24 KiB per batch; at most twenty applied batches and forty model exchanges per attempt, further bounded by existing request/time limits. finish_stage freezes the candidate and runs its stage gate. Functional failure begins the next attempt retaining edits and spending. Durable journal keys include task/attempt/batch, preventing duplicate application and completed-request resend after restart. Refresh actual hashes; preserve protected paths, scope, atomic writes and conflict detection.

### Protocol

Precise diagnostics for JSON, missing fields, action shape, stale hashes, size and context. At most two correction responses in the same attempt; the next protocol failure exhausts the attempt. Count every model request. Invalid replies apply nothing. Stale hash requires a fresh read, never automatic hash substitution. Preserve bounded raw responses and validation results. No ambiguous JSON repair, relaxed validation or extra attempts. Infrastructure errors stop with evidence instead of retrying product code.

## 3. Independent lifecycle

### Review and integration

Use the same effective stage checks in candidate, review and integration. Review only passing work. Intermediate integration runs current and previously accepted stage checks plus preflight invariants, excluding future final-only checks. Final integration runs the full project suite. Only reviewed/integrated stages unlock dependents. Review revisions return to DeepSeek within original IDs, deadlines and spending. Integration failure preserves evidence and requires supported repair.

### Monitoring

Durable v2 run phases: preparation, planning, implementation, review, integration, waiting-answer, blocked, paused, stopped, expired, completed. Derive from actual tasks, requests, ownership, dependencies and deadlines rather than an active label. Preserve the first blocker after later expiry. Coordinator monitors without periodic native Codex inference. Questions pause affected work and notify; never invent answers or expand scope. Known provider unavailability may wait at most thirty minutes within the original deadline; ambiguous inference remains uncertain and is never automatically resent. Hold a bounded macOS idle-sleep assertion while authorized overnight execution is active; release on pause, stop, completion or attention. Mac must remain powered and model reachable.

Observation accepts an optional starting cursor and returns a reusable continuation cursor. Inspect current state first; retain bounded calls and avoid replaying history. Observation timeout ends observation only; it does not end the job or imply a monitor handoff.

### Notifications and report

Reuse durable notifications. Local macOS alerts only for completion, blocker, uncertainty or a question, using fixed text and stable IDs. No progress spam, execution of model output, credentials or outbound communication. Record deliveries and failures. Saved report/dashboard remains authoritative when OS suppresses an alert. Auto-finalize only when all stages are reviewed/integrated and full final checks pass.

Deterministic morning report: result, launch instructions, branch/worktree, checks, reviews, usage, limits and evidence. Failure report names the first blocker and exact continuation decision. Local delivery only; publication/deployment/outreach/accounts need separate authority.

## 5. Verification and rollout gates

For each regression observe failure before fix:

- Exact-policy mismatch rejects undeclared input.
- Missing permissions rejects the whole plan with zero child records.
- Early stages need no future artifacts; final rejects missing deliverables.
- More-than-two-file stage uses multiple batches before its first gate.
- All four recovered raw failures produce diagnostics, bounded correction and exact spending.
- Crashes around request save, apply, checks, review and integration do not duplicate execution or reset state.
- History/output storms cannot terminate the independent run monitor.
- Blocker, question, outage, deadline and alert failure have durable honest state.
- Completion report and receipt are automatic.
- Old approval hashes and other three modes remain compatible.

Demonstrate actual DeepSeek, actual Codex review and revision, stage integration, full final suite and report while the originating chat is inactive. Deterministic failing fixture demonstrates blocked-alert handling. These numerical limits are a proposal, not authorization to dispatch. Tracker retry requires this release gate and a separate run approval. Never claim release-complete with pilot pending.
