# Mosaic in Codex

Give Codex a substantial coding task. Mosaic offers **Collaborative**, **DeepSeek-only**, **Codex-only**, and **Overnight review** once, then retains that goal's mode. You can also say “use Mosaic” or explicitly select `$frontier-harness`. Quick questions receive ordinary answers.

Codex summarizes the project, intended changes, protected checks and numerical limits before dispatch. Existing matching authorization is reused. New permissions or decisions are requested when needed. Internal IDs and manifests are available as details rather than work for the owner to copy.

Ask “how is it going?”, “pause this task”, “stop”, “continue”, or “open Mosaic”. The observer shows captured DeepSeek activity and reported Codex progress, with saved outcomes before raw evidence. First login may require pasting the viewer key copied locally by the opener. Keys never belong in chat.

## Mode boundaries

| Mode | Work and acceptance |
| --- | --- |
| Collaborative | Codex and DeepSeek implement in scoped candidates. Main Codex reviews and integrates. |
| DeepSeek-only | DeepSeek plans and implements; protected checks govern acceptance. No Codex implementation, review or fallback. |
| Codex-only | Native Codex work, with no DeepSeek calls. |
| Overnight review | DeepSeek implementation with bounded automatic Codex review after passing checks. |

Coding starts from a committed Git baseline and uses isolated worktrees. Existing edits are preserved; Mosaic explains any missing preparation without automatically staging or committing the owner's changes. A mode switch does not reset spending, deadlines or ownership. Unavailable providers remain visible blockers according to the selected mode.

The Mac coordinator starts at login. Idle startup dispatches no work. Collaborative supervision and native integration need an active chat; an inactive chat is not automatically awakened by an event. Only the overnight workflow provides automatic background review. The Mac must remain available for coding and checks.

## Installation and removal

One versioned standalone package provides four sibling skills and a single MCP bridge named `frontier-harness`. Private provider settings and current state remain outside the immutable package. Existing deployment checkpoints govern skill/launcher changes; separate exact records cover MCP, managed personal instructions and the login service. Installation preserves unrelated bindings.

The installed primary launcher supports `observer` with the same private launcher settings as its MCP connection. It opens the login-aware loopback home and copies only the viewer credential locally. Viewer access cannot approve or mutate work.

The private installation record identifies the exact newly introduced files, links, service and their hashes. Removal stops that owned service after quiescence, removes only exact introduced bindings and the exact managed instruction block, and retains current state, packages and evidence. Unknown or changed bindings stop removal for inspection. Never restore an older database or delete ownership to undo spending.
