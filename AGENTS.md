# Frontier Orchestrator project guidance

For explicitly selected collaborative or Codex-only goals, main Codex and native implementers may write substantial code in separately owned candidates. The review-only role language below applies to the preserved legacy overnight mode. See the current opt-in direction in docs/PRODUCT_CONTEXT.md. The November 4 coding-core delivery is separately scoped; research remains parked and historical execution packets grant no fresh authority.

Before project questions or changes, read `docs/PRODUCT_CONTEXT.md` and `docs/MVP.md`, then read `PROJECT_MEMORY.md` when present. The memory file is intentionally ignored by Git and contains the owner's machine-specific handoff; the tracked docs are the public handoff. Keep confirmed facts, proposals, and unknowns distinct. Date and recheck details that can change, including endpoint reachability, model ID, repository revision, and runtime settings. Update local memory after a durable decision or verified integration. Never record credentials.

The product goal is a frontier-reviewed delegation loop: the local model plans and does bounded work, and the frontier model independently reviews evidence and requests focused revisions. The coordinator owns task state, plan versions, limits, permissions, and the event log. Frontier (Codex) usage is the scarce resource: in the coding workflow Codex normally reviews only after checks pass. The owner also allows one explicit, optional pre-stage guidance call when needed. Codex must not write routine assignments or edit code. DeepSeek doing slower work is acceptable; exhausting the Codex window is not.

The first live milestone is a Mac terminal project-design handoff: Codex plans, DeepSeek answers one focused assignment, and Codex reviews with at most one local revision. That text-only workflow keeps one Codex planning call per job; the scoped coding workflow defaults to DeepSeek planning and check-gated Codex review, with optional one-call guidance before a stage starts. Build the scoped coding workflow next, then the browser interface. Keep the code workspace and tool execution location explicit. Do not treat text generated by a model as authorization to execute commands, edit files, or expose files to a cloud provider.

The separate `Local LLM` project documents DeepSeek deployment and tuning. The two Sparks currently run one distributed DeepSeek service, not two independent local agents. Do not change their runtime configuration as part of this application's implementation unless the user specifically asks. Keep machine-specific addresses, paths, tuning observations, and credentials out of tracked files; the repository is intended for a future public release.
