# Frontier Orchestrator project guidance

Before project questions or changes, read `docs/PRODUCT_CONTEXT.md` and `docs/MVP.md`, then read `PROJECT_MEMORY.md` when present. The memory file is intentionally ignored by Git and contains the owner's machine-specific handoff; the tracked docs are the public handoff. Keep confirmed facts, proposals, and unknowns distinct. Date and recheck details that can change, including endpoint reachability, model ID, repository revision, and runtime settings. Update local memory after a durable decision or verified integration. Never record credentials.

The product goal is a frontier-led delegation loop: the frontier model plans, assigns bounded work to a local model, receives evidence, and reviews or requests revisions. The coordinator owns task state, plan versions, limits, permissions, and the event log.

The first live milestone is a Mac terminal project-design handoff: Codex plans, DeepSeek answers one focused assignment, and Codex reviews with at most one local revision. Build the scoped coding workflow next, then the browser interface. Keep the code workspace and tool execution location explicit. Do not treat text generated by a model as authorization to execute commands, edit files, or expose files to a cloud provider.

The separate `Local LLM` project documents DeepSeek deployment and tuning. The two Sparks currently run one distributed DeepSeek service, not two independent local agents. Do not change their runtime configuration as part of this application's implementation unless the user specifically asks. Keep machine-specific addresses, paths, tuning observations, and credentials out of tracked files; the repository is intended for a future public release.
